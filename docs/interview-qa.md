# 面试 Q&A 清单

> 每个问题给「主答案」+「可能的追问」，力求经得起深挖。对应实现细节见 `design.md` / `concurrency.md`。

---

## 1. 为什么用 NIO？（vs 传统 BIO）

**主答案**：BIO（阻塞 IO）一个连接一个线程，1000 个连接就需要 1000 个线程，每个线程默认 1MB 栈 → 内存和上下文切换都扛不住。NIO 用**少量线程管理大量连接**：Acceptor/Poller 线程负责连接的就绪检测，工作线程池只处理「有数据可读」的请求，所以「连接多 ≠ 线程多」。本项目压测实证：1000 并发、6000 请求、0 错误、无连接拒绝。

**追问「那 NIO 也有工作线程，请求多了不还是要排队吗？」**：对，NIO 解决的是「连接管理」的线程开销，不是「计算」的线程开销。工作线程数（maxThreads）仍要按 CPU 密集 vs I/O 密集的比例来定，压测里 200→800 线程，I/O 密集的下载/列表 P99 下降、CPU 密集的登录反而上升（上下文切换），就是这个道理。

## 2. 乐观锁 vs 悲观锁？怎么选？

**主答案**：乐观锁不占行锁、冲突时重试，适合**冲突概率低**的场景；悲观锁（`SELECT ... FOR UPDATE`）占行锁、串行化，适合**冲突高 + 临界区长**的场景。

- 配额扣减用乐观锁（version 重试）：单用户配额冲突概率低，且上传事务含磁盘 I/O，悲观锁会长时间锁住 user 行。
- 秒传引用计数用悲观锁：`ref_count` 是跨用户共享的读改写，秒传要「插入新行 + 多行更新」，单条 CAS 表达不了。

**追问「乐观锁重试为什么可能失败？」**：MySQL 默认 REPEATABLE READ 下，事务内普通 SELECT 读快照，重试的再读会读到旧 version，永远重试不成功。所以扣配额事务改 READ_COMMITTED，让再读拿到最新提交数据。（见 `concurrency.md` §1）

## 3. 秒传原理？

**主答案**：客户端先算文件 MD5（SparkMD5 分片读，不阻塞主线程）→ 调秒传接口 → 服务端按 MD5 查重（`FOR UPDATE` 锁 canonical 行）→ **命中**则复用已有物理文件 + 引用计数 +1，秒回不传文件本体；**未命中**才走正常上传。

**追问「为什么客户端算 MD5，不服务端算？」**：秒传要省的是带宽——服务端算 MD5 意味着文件已经传上来了，就没意义了。客户端算好 MD5，只把 32 字节哈希发过去问「你有没有」，命中就零上传。

**追问「客户端能伪造 MD5 吗？」**：能。所以严肃场景服务端要在落盘时重算校验，或者只把客户端 MD5 当「去重提示」而非「完整性质检」。本项目分片合并时服务端会重算整文件 MD5 比对；普通上传信任客户端 MD5（记为阶段 7 可加强点）。

## 4. Range 原理（206 断点下载）？

**主答案**：HTTP 协议允许请求头带 `Range: bytes=start-end`，服务端解析后只返回该区间，响应 `206 Partial Content` + `Content-Range: bytes start-end/total` + `Accept-Ranges: bytes`。断点下载（续传）和浏览器拖动视频进度条都依赖它。

**追问「服务端怎么只吐一段？」**：流式输出前用 `InputStream.skip(start)` 跳到起始位置，再只读 `length` 字节写响应。全程分块读写，不把文件整读内存。

## 5. 千人在线如何撑住？

**主答案**：四件事——① NIO 线程模型（连接多≠线程多）；② 全链路流式 I/O（大文件不整读内存，工作线程快速释放回池）；③ JWT 无状态会话（不占服务端内存）；④ 合理的线程池/连接参数调优。压测报告有数据支撑。

**追问「瓶颈在哪？」**：单机下是 CPU（BCrypt 登录密集）+ 磁盘 I/O（上传下载）。要再往上，加核/分布式、BCrypt 降 cost、文件走对象存储/CDN、数据库读写分离。

## 6. 引用计数怎么保证并发正确？

**主答案**：`ref_count` = 指向同一 `storage_key` 的文件行数。秒传用 `SELECT ... FOR UPDATE`（按 `ORDER BY id LIMIT 1` 锁最早的 canonical 行）串行化同一内容的并发秒传；删除用单条原子 `UPDATE ... ref_count=ref_count-nDel` 递减，归零才删物理文件。

**追问「为什么 `ORDER BY id LIMIT 1`？」**：保证并发请求锁**同一行**——如果各锁各的行，串行化就失效了。

## 7. 分片上传 + 断点续传原理？

**主答案**：`创建会话 → 前端 `File.slice` 切片并发上传 → 合并`。断点续传靠 `init` 按 `(userId, md5, parentId, status=0)` **幂等复用会话**并返回已传分片，客户端只补缺失片——刷新页面/中断重传自动续上。合并时服务端边写边算 MD5 校验完整性，成功才扣配额写元数据。

**追问「为什么断点续传要服务端驱动，不前端存 sessionId？」**：前端 localStorage 存 sessionId 清缓存就丢了；按内容 MD5 幂等，重试天然命中同一会话，更健壮，也是更硬的面试点。

## 8. 为什么不整读内存（流式 I/O）？

**主答案**：大文件若整读进内存，一个 5GB 上传就能打爆堆内存，还会长时间占用工作线程。本项目上传/下载/分片/合并全程分块读写（8KB 缓冲），内存占用 O(1)，工作线程处理快、及时回池。

## 9. 路径穿越怎么防？

**主答案**：`storage_key` 不存原始文件名（用 `userId/日期/uuid`），且 `resolve` 时 `normalize` 后校验仍以存储根目录为前缀，拒绝 `../` 逃逸。

## 10. SQL 注入怎么防？

**主答案**：MyBatis 全部用 `#{}` 预编译参数（PreparedStatement 占位符），不拼接 SQL；用户输入不进 SQL 字符串。

## 11. JWT vs Session？

**主答案**：Session 状态存服务端，千人在线占内存、还要考虑分布式共享；JWT 无状态、客户端持有、服务端只验签，天然水平扩展。代价是没法主动踢人（靠短过期 + 前端删 token）。

## 12. BCrypt 为什么加盐？

**主答案**：BCrypt 自带随机盐 + 慢哈希（cost 参数），同一密码两次哈希结果不同，防彩虹表；慢哈希抬高暴力破解成本。

## 13. 同名文件并发怎么处理？

**主答案**：前置 `findByNameAndParent` 校验是 TOCTOU（检查与插入有竞态），所以加 `UNIQUE(user_id, parent_id, name)` 兜底 + 全局异常把 `DuplicateKeyException` 转 400。前置校验是体验优化，唯一约束才是正确性保证。

## 14. 事务隔离级别为什么用 READ_COMMITTED？

**主答案**：乐观锁重试依赖「再读看到最新 version」。REPEATABLE READ 下事务内普通 SELECT 读的是固定快照，重试的再读会读到旧 version，乐观锁永远重试不成功；READ_COMMITTED 每次 SELECT 读最新已提交数据，重试才能推进。

## 15. 全链路是怎么防超卖配额的？

**主答案**：扣配额不是「读→判断→写」三步（会超卖），而是单条 `UPDATE ... WHERE quota_used+delta<=quota_limit AND version=?`，把「检查 + 扣减」压成一条原子语句，再配 version 重试兜底。压测 20 并发秒传、配额上限 300B，结果 `quota_used` 精确不超卖。
